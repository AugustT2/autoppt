# PPT 数据更新与智能化取数 — 方案文档

> 本文档整理自需求沟通结论，用于研发落地与后续迭代对齐。  
> 实现集中在 **`com.example.pptrefresh`**（Apache POI 写 pptx），不绑定具体厂商 LLM。  
> **技术架构**见 [`ppt-data-refresh-technical-architecture.md`](./ppt-data-refresh-technical-architecture.md)。

---

## 1. 背景与目标

### 1.1 业务背景

公司其他部门已有**成品 PPT**（模板样式已定），需周期性**更新其中的数据**，且：

- **表格样式不能动**（字体、边框、合并、列宽等保持模板原样），仅更新**单元格内的值**。
- **图表**在现阶段仅更新**数据点/系列数值**（系列数量、图表类型与模板一致），不做增删系列等结构变更。
- **文本框**内容需更新；数据来自**外部接口**（JSON），且**一个文本框可能对应多次 API 调用**；需**超时与重试**。
- **时间口径**（如「最新日期」「最新季度」）尚未完全敲定，需支持**后期在配置中扩展**；首期可提供两条占位规则。

### 1.2 核心目标

在**不要求业务部门治理 PPT 文件**（例如批量重命名形状、加占位符）的前提下，实现：

1. **按规则解析**输入 pptx 与文件名，选择对应配置；
2. **通过配置描述「写哪里 + 业务意图」**，由 **LLM 在工具（Tool / MCP）集合中选择调用方式并完成取数**；
3. **Java（或同一代码路径）负责校验、调用真实接口、将结果写回 pptx**；
4. 交付物为：**复制原 pptx → 在副本上更新 → 输出新文件**。

## 2. 范围与非目标（首期）

### 2.1 范围内

| 维度 | 说明 |
|------|------|
| 文本 | 允许使用页面上**已有固定字样作为锚点**；支持**仅替换锚点之后内容**或**整段替换**（需在配置中声明模式）。 |
| 表格 | **仅替换已有单元格的值**；**不考虑**行/列增减（后续若需要另起规格）。 |
| 图表 | **仅替换数字**；系列结构、图表类型与模板保持一致。 |
| 文件名 | 严格约定见第 4 节；用于**类型路由**与**白名单校验**。 |
| 配置 | **配置文件驱动**；业务口述需求，由研发维护配置文件；**整份 pptx 共用一套规则**；可变输入以**产品名称**等为主。 |

### 2.2 非目标（首期明确不做或弱承诺）

- **不要求**业务部门对 ppt 做「技术治理」（统一命名形状、加 `{{placeholder}}` 等）。
- **不**由 LLM 直接编辑 pptx 二进制或大块 Office XML；**写盘一律走确定性代码**（如 Apache POI）。
- **不**在首期配置中维护「每种 PPT 手写对应哪个 HTTP 路径」的庞大路由表；**接口选择优先交给 LLM + 全局 Tool/MCP**（见第 8 节）。

## 3. 总体架构原则（已对齐）

以下三句话作为**架构红线**，后续实现与 Code Review 均以此为据：

1. **YAML 描述「写哪里」与「写什么意图」**  
   - **写哪里**：页码、锚点文本、第 N 个表格/图表、替换模式等。  
   - **写什么意图**：自然语言说明所需数据语义（**不写**具体「调哪个 REST 路径」作为硬编码路由）。

2. **LLM 决定「怎么取数」**  
   - 在已注册的 **Tool / MCP** 集合中，根据意图与上下文（产品名、已解析的时间口径等）选择工具并生成参数；可支持多步、多工具。  
   - **首期策略**：**全局 Tool 列表**全部可见；线上观测 **误调率** 后，再引入 **「软收窄」**（例如检索/规则从全局集合筛 Top-K 工具再喂给模型），**不改变「YAML 不写 API 路由表」的原则**。

3. **Java 只负责「校验与写盘」**  
   - 校验 LLM 输出 / Tool 调用是否符合 **JSON Schema**（或等价强类型约束）；执行 HTTP/MCP；聚合结果；**按 YAML 定位信息写回 pptx**。

### 3.1 提示词是否按 PPT 类型拆分？

**不必须**为每种类型维护一整套完全不同的 **System Prompt**。

推荐结构：

| 层级 | 做法 |
|------|------|
| **System（底座）** | **全局统一一份**：角色、仅用已注册工具、输出必须为可解析结构、禁止编造未定义字段、重试与失败时行为等。 |
| **按类型 / 按文件差异** | 主要落在 **各类型 YAML** 的任务列表中：每条任务有不同的**意图描述**与**落点**；这些内容作为 **User 侧上下文** 拼入即可。 |
| **可选补强** | 某类型误调率高时，可在 YAML 增加短 **`hints` / `styleNotes`**（数行），或极短的 **type 后缀** 拼入 prompt；**按需增加**，避免 N 份大段 prompt 分叉维护。 |

## 4. 文件名、类型键与校验

### 4.1 切分规则

- 取文件名 **去掉扩展名 `.pptx`** 后的 **basename**。  
- 按 **连字符 `-`** 切分为若干 **段（segment）**。

### 4.2 段数与错误策略

- **必须恰好为 3 段**；否则 **一律报错**（不忽略、不兜底）。  
  - 段数不足：报错。  
  - 段数过多：报错。

### 4.3 段语义与类型键

| 段序号（从 1 开始） | 含义（约定） |
|---------------------|--------------|
| 第 1 段 | 前缀信息，例如 `20260430`（具体业务含义可后续在配置或规则中再绑定）。 |
| 第 2 段 | 参与类型；须落在 **段2 允许列表** 中。 |
| 第 3 段 | 参与类型；须落在 **段3 允许列表** 中。 |

**类型键（`deckType`）**：

- 拼接规则：**第 2 段 + `-` + 第 3 段**（中间**再插一个 `-`**，与视觉上的「类型两段」对齐）。  
- 示例：`20260430-混合固收+-M1.pptx`  
  - basename：`20260430-混合固收+-M1`  
  - 三段：`20260430` | `混合固收+` | `M1`  
  - `deckType`：**`混合固收+-M1`**

### 4.4 白名单校验

- **第 2 段、第 3 段** 各自维护 **允许取值列表**（可与类型键联合校验）。  
- 任一段不在白名单：**报错**，避免静默匹配到错误规则文件。

### 4.5 配置路由

- 使用 `deckType` 映射到 **该类型的 YAML 规则文件**（路径约定由实现时定，例如 `rules/混合固收+-M1.yaml` 需处理文件系统对 `+` 等字符的转义或哈希别名策略）。

## 5. 配置文件格式建议

### 5.1 YAML 与 JSON

- **推荐主格式：YAML**  
  - 利于业务与研发阅读、**注释**、嵌套规则说明。  
  - 缺点：缩进敏感；必须通过 **Schema 校验 + CI** 在合并前拦截低级错误。

- **JSON** 可作为等价物或机器生成物；若业务不直接编辑文件，JSON 也可，但可读性与注释较弱。

- **推荐组合**：**YAML 编写 + JSON Schema（或同类）校验同一逻辑结构**；加载后统一校验再执行。

### 5.2 YAML 应包含的信息（逻辑模型）

下列为**逻辑字段**，具体键名实现时可调整，但语义建议保留：

- **元数据**：`deckType`、版本、负责人、说明。  
- **变量**：如 `productName` 来源（命令行 / 上游系统）。  
- **时间规则引用**：如 `latestQuarter`、`latestDate`（首期可为占位实现，见第 9 节）。  
- **任务列表 `tasks`**（按页或全局有序）：  
  - `slideIndex`（约定 0 或 1 起始需在项目内统一并文档化）。  
  - **文本类**：`anchorText`、`mode`（`after_anchor` | `replace_all` 等）、`intent`（自然语言）。  
  - **表格类**：`tableOrdinal`（该页第 N 个表）、`cellMappings` 或「整块表意图 + 由 LLM 返回矩阵再校验行列数」等（首期以「仅换已有格」为准）。  
  - **图表类**：`chartOrdinal` 或等价定位、`intent`。  
  - **可选**：`hints` 字符串，用于降低误调。  
- **（不在首期硬编码）**：**不写**「URL + 固定 query」作为每种 deck 的维护重点；取数路径交给 LLM + Tool。

## 6. PPT 定位策略（不接受模板治理）

### 6.1 约束与事实

- 业务部门**不接受**对成品 ppt 做批量「技术治理」（如统一命名形状、加占位符），认为增加负担。  
- 单份 ppt 内 **表格 / 图表数量较少**（沟通中：约 **3～4 个**），有利于用**序号定位**。

### 6.2 推荐策略

| 对象 | 策略 | 风险说明 |
|------|------|----------|
| **表格 / 图表** | **页号 + 该页上第 N 个** 表格/图表（遍历顺序需在 POI 层约定并与文档一致）。 | 若有人增删形状，序号可能错位 → **版式变更可能需要同步改 YAML**；需在运维文档中写明。 |
| **文本** | **锚点**：页面上已存在的**固定连续字样**；再按配置选择「锚后替换」或「整段替换」。 | 若业务修改锚点文案 → 匹配失败；需在运行前做 **锚点存在且唯一性** 校验并给出清晰错误信息。 |

### 6.3 锚点唯一性

- 必须在规范中约定：同一锚点在指定作用域内（整页 / 某文本框）**必须唯一**；否则 **报错** 或要求配置指定消歧策略（首期可简化为 **报错**）。

## 7. 数据获取、LLM 与 Tool / MCP

### 7.1 API 与 JSON

- 外部系统以 **JSON** 返回；Java 侧解析后与写回逻辑对接。  
- **一个文本框**可能触发 **多次 API**（多轮 tool 调用或编排）；需 **超时、重试、退避** 策略（默认值可在全局配置中定义）。

### 7.2 LLM 与 Tool / MCP 边界

- **Tool** 或 **MCP** 暴露「取数能力」，由 LLM 在给定上下文中选择。  
- **首期**：**全局注册所有 Tool**，全部对模型可见。  
- **演进**：根据线上 **误调率、成本、延迟**，增加 **软收窄**（例如基于意图 embedding 检索 Top-K 相关 tool 再调用模型），**不回到**「每种 PPT 维护一张 API 对照表」的强耦合模式，除非误调无法通过收窄与 hints 解决。

### 7.3 安全与可观测

- **鉴权**：Tool/MCP 调用携带服务账号或用户令牌（由部署架构决定，**密钥不得写入 YAML**）。  
- **审计日志**：记录 `deckType`、任务 id、选用的 tool、参数摘要（脱敏）、耗时、成功/失败原因，便于业务与研发追溯。

## 9. 交付流程与失败策略

### 9.1 交付流程

1. **校验文件名** → 得到 `deckType` 并加载 YAML（Schema 校验）。  
2. **复制**输入 pptx 为工作副本。  
3. 打开副本，按任务顺序：  
   - 组装上下文（产品名、时间规则解析结果、任务 intent 等）；  
   - 调用 LLM → 得到 tool 调用计划；  
   - Java **校验** → 执行 tool → 得到数据；  
   - **确定性写回** pptx。  
4. 写出 **新 pptx** 路径（命名规则由实现或运维约定：如加时间戳、产品名等）。

### 9.2 失败策略

- **文件名不合法 / 白名单不通过 / YAML Schema 失败 / 锚点校验失败 / Tool 输出 Schema 失败**：**整单失败**，**不产出半成品 pptx**（工作副本不写入最终输出路径，或删除未完成的副本）。  
- **失败诊断文件**：在**输出目录**（与成功时 pptx 同级）写入 **`.failed.json`**，便于运维与业务排障；成功任务**不写**该文件。  
- **API 超时重试**：在单任务级配置重试次数与总超时；仍失败则按上条整单失败（首期建议 **失败即停** 以便发现问题）。

### 9.3 失败诊断文件（`.failed.json`）

| 项 | 约定 |
|------|------|
| **触发** | 任一步导致整单失败时（含文件名、YAML、锚点、LLM/Tool、写回、保存等）。 |
| **位置** | 与本次任务配置的 **输出目录** 相同；与预期输出 pptx **同 basename**（仅扩展名不同）。 |
| **命名** | `{预期输出pptx主文件名}.failed.json`。例：预期输出 `20260430-混合固收+-M1-产品A-out.pptx` → `20260430-混合固收+-M1-产品A-out.failed.json`。 |
| **格式** | JSON；UTF-8；字段建议见 [`ppt-data-refresh-technical-architecture.md`](./ppt-data-refresh-technical-architecture.md) §9.3。 |
| **内容原则** | 含 **失败阶段、错误码、可读 message、traceId/jobId**；可含 **deckType、taskId、slideIndex**；**不写入** ppt 全文、API 密钥、未脱敏的敏感业务字段。 |

## 10. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 锚点被业务改字 | 运行前校验；错误信息包含页码与缺失锚点；失败时 **`.failed.json`** 携带定位信息；必要时在 YAML 增加 `hints`。 |
| 表格/图表序号因改版错位 | 文档声明「版式变更需更新配置」；版本化存储 YAML。 |
| LLM 误选 tool 或幻觉参数 | 全局 Schema 校验 + 重试；观测误调率后 **软收窄**；关键路径后期可部分固化到代码而不改用户流程。 |
| 成本与延迟 | 缓存相同 tool+参数结果；任务批处理与并发上限；软收窄减少 token。 |

- MCP 与 Java 进程的 **部署拓扑**（同进程 vs 独立 Agent 服务）。

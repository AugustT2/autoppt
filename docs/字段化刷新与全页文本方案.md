# 字段化刷新与全页文本方案（设计备忘）

> **状态**：设计讨论记录，**尚未实现**。  
> **背景**：`偏债混-M1` 等 deck 出现「标题框 / 正文框分离」等版式后，单靠 `anchorText` + `after_anchor` 难以表达「锚点在一个框、要改的是另一个框」；同时希望 YAML 更贴近业务——**列清楚要更新哪些数据**，而不是逐个 shape 写锚点。  
> **相关文档**：[`ppt-data-refresh-design.md`](./ppt-data-refresh-design.md)、[`产品名称提取方案.md`](./产品名称提取方案.md)、[`Tool约束与注册方案.md`](./Tool约束与注册方案.md)。

---

## 1. 问题与动机

### 1.1 现状（已实现）

每个 **task** 绑定一种 **写回类型**（`text` / `table` / `chart`），并通过以下方式 **定位**：

| 类型 | 定位方式 |
|------|----------|
| text | `anchorText` 找到**包含该字样**的唯一文本框；`mode` 为 `replace_all` 或 `after_anchor` |
| table | `tableOrdinal` |
| chart | `chartOrdinal` |

`after_anchor` 语义：在**同一个文本框**内，保留「锚点及之前」的原文，用 LLM/Stub 返回的字符串替换「锚点之后」的内容（见 `PptWriteService.applyText`）。

### 1.2 典型痛点

1. **锚点与写回目标不在同一文本框**  
   例：框 A 只有「基金基本情况」标题；框 B 才是「偏债混-产品名 + 基金类型 + …」。  
   此时 `anchorText: "基金类型："` 必须写在 B 里才生效，无法「用 A 定位、改 B」。

2. **YAML 偏「物理位置」、偏「业务字段」**  
   产品更关心：更新标题、基金类型、成立日、收益率表、资产配置图……  
   而不是：第几个锚点、after_anchor 从哪一字开始切。

3. **LLM 调用次数多**  
   当前每个 task 一轮对话（偏债混-M1 约 5 个 task），延迟与成本随 task 数线性增长。

4. **「读全文」的误解**  
   「读取所有文本」应指：**给认知层（LLM）提供整页上下文**；**不是**用一整段字符串替换整页或整份 PPT。

## 2. 目标形态（概念）

### 2.1 两层职责分离

```
┌─────────────────────────────────────────────────────────┐
│  认知层契约：本页要更新哪些「业务字段」(fields)            │
│  输入：slide 文本快照 + productCode + 时间上下文 + intent  │
│  输出：结构化 JSON（按 field 键名）                        │
└───────────────────────────┬─────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────┐
│  写回映射层（固定、可版本化）：field → POI 写回目标        │
│  例：fund_type → 正文框 textOrdinal:2, replace_all       │
│      yield_ranking_table → tableOrdinal:1                │
└───────────────────────────┬─────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────┐
│  文档层（现有）：PptWriteService / ChartDataWriter 等     │
└─────────────────────────────────────────────────────────┘
```

**原则**：对 LLM 暴露 **字段**；对 POI 仍走现有 **text / table / chart** 写回，中间增加 **FieldWritePlan**（名称待定）。

### 2.2 「读取所有文本」指什么

| 层次 | 内容 | 用途 |
|------|------|------|
| **Slide 纯文本** | 指定页所有文本框 `getText()` 拼接或分段列表 | LLM 理解当前页已有文案、避免改错块 |
| **结构摘要（可选）** | 表行列数、图 series 数、文本框序号与大致坐标 | 校验 LLM 输出形状、辅助映射消歧 |
| **不写回全文** | — | 禁止「模型输出整页 HTML/全文」直接覆盖 slide |

首期一页四象限（`偏债混-M1`）体量可控；多页 deck 应按 `slideIndex` 分片，避免单次 prompt 过长。

## 3. YAML 形态（草案，未实现）

### 3.1 逻辑 task：按字段声明

```yaml
tasks:
  - id: slide0_refresh
    type: slide_data          # 新概念；与现有 text/table/chart 并列或作为编排入口
    slideIndex: 0
    fields:
      - title
      - product_line_display   # 如「偏债混-蓝海稳健增长混合A」或拆成 prefix + displayName
      - fund_type
      - inception_date
      - latest_aum
      - fund_managers
      - benchmark
      - risk_level
      - custodian
      - yield_ranking_table
      - allocation_chart
      - nav_chart
    intent: "按 fields 从数据源取数；保留模板版式，仅更新值"
```

`fields` 列表 = **本 task 负责刷新的业务数据项**（对人与对 LLM 的契约）。

### 3.2 写回映射表（与 fields 配套）

建议放在同一 deck YAML 的 `fieldBindings:`（或独立 `bindings/偏债混-M1.yaml`），**不交给 LLM 修改**：

```yaml
fieldBindings:
  title:
    type: text
    slideIndex: 0
    anchorText: "基金业绩说明"
    mode: replace_all

  product_line_display:
    type: text
    slideIndex: 0
    textOrdinal: 2          # 示例：第 2 个文本框为「基金基本情况」正文块
    mode: replace_all

  fund_type:
    type: text
    slideIndex: 0
    textOrdinal: 2
    mode: replace_all       # 或与 product_line_display 合并为一块正文的一次性 replace

  yield_ranking_table:
    type: table
    slideIndex: 0
    tableOrdinal: 1

  allocation_chart:
    type: chart
    slideIndex: 0
    chartOrdinal: 1

  nav_chart:
    type: chart
    slideIndex: 0
    chartOrdinal: 2
```

说明：

- **fieldBindings** 解决「两框分离」：标题框、正文框用不同 `textOrdinal` 或不同锚点，无需 `after_anchor` 跨框。
- 多个 field 指向同一 `textOrdinal` 时，编排层应 **合并为一次写回**（例如拼成多行正文），避免后写覆盖前写。

### 3.3 与现有 `偏债混-M1.yaml` 的对应关系

| 现有 task id | 可映射 field（示例） |
|--------------|---------------------|
| title | title |
| fund_meta | product_line_display + fund_type + … + custodian（可拆多个 field 或一个 `fund_meta_block`） |
| yield_ranking_table | yield_ranking_table |
| allocation_chart | allocation_chart |
| nav_chart | nav_chart |

`productNameResolution`（LLM_EXTRACT / ANCHOR_REGEX）**保持不变**，仍在各 task 之前解析 `productDisplayName`。

## 4. 运行时流程（目标）

1. 解析文件名、加载 deck 规则、解析产品名与时间上下文（**不变**）。
2. **收集 slide 文本快照**（+ 可选结构摘要），写入 `TaskContext` 或单次 LLM 请求的 user 消息。
3. **一次**（或按 slide 一次）LLM / Tool 调用，按 `fields` 返回 JSON，例如：

```json
{
  "title": "基金业绩说明（蓝海稳健增长混合A）",
  "product_line_display": "偏债混-蓝海稳健增长混合A",
  "fund_type": "偏股混合型基金",
  "inception_date": "2019-06-12",
  "latest_aum": "58.6 亿元",
  "fund_managers": "张明、李悦",
  "benchmark": "沪深300指数收益率×70% + 中债综合指数×30%",
  "risk_level": "R3（中风险）",
  "custodian": "示例商业银行",
  "yield_ranking_table": { "cells": [["区间","收益率", "..."], ["近一年","+12.8%", "..."]] },
  "allocation_chart": {
    "categories": ["2024Q2", "..."],
    "seriesNames": ["股票", "债券", "现金及其他"],
    "seriesValues": [[68.2, 71.5], [22.5, 19.8], [9.3, 8.7]]
  },
  "nav_chart": { "...": "..." }
}
```

4. **Schema 校验**：字段齐全性、表行列数、图 series 长度与模板 `SlideStructure` 一致（可复用/扩展 `WritePayloadValidator`）。
5. 按 **fieldBindings** 展开为多条 `TaskWritePayload`，调用现有 `PptWriteService.apply`。
6. 保存 pptx（**不变**）。

## 5. 与「仅锚点方案」的对比

| 维度 | 现状：每数据一块一个 task + anchor/ordinal | 字段化 + 全页文本 |
|------|------------------------------------------|-------------------|
| YAML 可读性 | 偏 POI 定位 | 偏业务字段 |
| LLM 调用次数 | ≈ task 个数 | 可 1 次/slide（或 1 次/deck） |
| 两框/多框版式 | 锚点必须在被改框内 | 映射表用 textOrdinal / 下一框关系 |
| 定位稳定性 | 锚点文案变更即失败 | 映射表变更；文本快照辅助 LLM |
| 实现复杂度 | 已落地 | 需 fieldBindings、展开器、合并写回 |
| 失败诊断 | 按 taskId | 需 field 级错误码 |

## 6. 其他定位策略（备忘，可选）

在 **不采用字段化** 或 **映射表补充** 时，可单独选用：

| 策略 | 说明 | 适用 |
|------|------|------|
| **改模板** | 把「基金类型：」放进将被替换的正文框 | 零代码，首选 |
| **textOrdinal** | 第 N 个文本形状，`replace_all` | 版式固定、框顺序稳定 |
| **anchor + next_text_shape** | 锚点框 A 定位，写回遍历顺序上的下一文本框 B | 标题/正文两框 |
| **shapeName** | 模板制作时命名形状，按 name 查找 | 长期最稳，需模板规范 |

字段化方案 **不排斥** 上述策略：它们落在 **fieldBindings** 层即可。

## 7. 风险与约束

1. **不能完全取消「写哪里」**  
   fields 只解决「更新什么」；**fieldBindings** 必须存在且随模板版本维护。

2. **LLM 输出必须结构化**  
   禁止自由散文；需 JSON Schema / 校验 + 失败重试；与现有 Tool 返回 JSON 的习惯一致。

3. **同框多 field 合并**  
   需定义合并规则（换行、标签前缀「基金类型：」等），避免多次 `setShapeText` 互相覆盖。

4. **样式**  
   正文多 field 合并写回时，仍应走 `TextStylePreserver` 多段落逻辑，避免首段加粗污染全文（见已实现修复）。

5. **图表/表**  
   仍为独立写回路径；字段 JSON 中嵌套 `cells` / `seriesValues` 与现有 `TaskWritePayload` 对齐。

6. **成本**  
   单次大 prompt 可能更省轮次但 token 更多；需按 slide 分片与缓存 Tool 结果。

## 8. 分阶段落地建议

| 阶段 | 内容 | 改动量 |
|------|------|--------|
| **A** | 保持现有 5 task；仅在 `TaskContext` / Prompt 中附带 **slide 纯文本快照** 作 LLM 参考 | 小 |
| **B** | YAML 增加 `fields` + `fieldBindings`；编排层 **展开** 为现有 task 序列（语法糖），LLM 仍可按 task 调用 | 中 |
| **C** | 每 slide **一次** LLM 返回整页 JSON + field 级校验 + 映射写回 | 大 |

**建议**：若短期只需解决「基金基本情况」与正文两框，可先在 **fieldBindings** 思路下用 `textOrdinal` 落映射（阶段 B 子集），再决定是否合并为单次 LLM（阶段 C）。

---

## 9. 非目标（本方案）

- 不通过「全文替换」绕过 POI 形状级写回。  
- 不要求业务部门批量重命名形状（除非采用 shapeName 策略）。  
- 不改变「表不增删行列、图不增删系列」的首期约束。
